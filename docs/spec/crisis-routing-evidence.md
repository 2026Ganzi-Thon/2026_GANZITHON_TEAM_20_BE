# S-16 위기 안내 분기 근거

2026년 11월 16일 기준 구현 초안. 걱정 제출 이후 일반 AI 콘텐츠를 만들기 전에 S-16 안내를 선택할지 결정한다. 임상 판단, 개인의 자살·자해 가능성 예측, 자동 신고와 전화 연결은 이 분기의 범위 밖이다.

## 근거와 구현에 적용한 범위

- WHO는 자살·자해 생각을 심한 고통을 겪는 신호로 설명하고, 삶을 끝내려는 생각이나 계획을 말하는 행동을 주요 신호로 제시한다. 서비스에서는 사용자 본인의 직접적인 표현과 행동·계획 표현을 안내 경로의 후보로 삼는다. [WHO Suicide Q&A](https://www.who.int/news-room/questions-and-answers/item/suicide)
- 미국 NIMH는 죽고 싶다는 말, 자살 계획을 세우거나 방법을 찾는 행동을 경고 신호로 든다. 걱정 제출 텍스트에서 이러한 신호가 직접 드러나면 일반 생성보다 S-16을 앞세운다. 구체적인 수단을 나열하거나 묻는 기능은 없다. [NIMH Warning Signs of Suicide](https://www.nimh.nih.gov/health/publications/warning-signs-of-suicide)
- NICE NG225 1.6절은 위험 점수나 저·중·고 분류를 사용해 미래의 자살·자해를 예측하지 않도록 권고한다. 이 앱은 불안도, 특정 단어 하나, 점수로 S-16 안내를 결정하지 않는다. [NICE NG225 1.6](https://www.nice.org.uk/guidance/ng225/chapter/recommendations#risk-assessment-tools-and-scales)
- 위 근거는 신호와 판단의 한계를 설명한다. 한국어 문구 패턴과 모호한 입력을 어떻게 처리하는지는 [앱의 화면 정책](screen_policy.md#10-위기-대응)을 반영해 정한 구현 규칙이며, 위 기관이 검증한 기준으로 볼 수 없다.

## 앱 분기 조건

1. 걱정 원문을 유니코드 정규화한 뒤 문장 단위로 본다. 불안도와 메모는 판정에 사용하지 않는다.
2. 죽고 싶은 의사, 자신을 해치려는 의도·계획, 직접 보고한 행동이 표현되고 해당 문장에 부정·인용·타인·과거 맥락이 드러나지 않으면 `SUPPORT_GUIDANCE`와 `S16`을 반환한다. 다른 문장의 직접 신호도 독립적으로 본다.
3. 신호 후보가 있지만 화자·시점·부정·인용 맥락이 모호하거나 분기 로직이 실패하면 `ASSESSMENT_FAILED`를 반환한다. 일반 생성 요청과 걱정 저장은 두 경우 모두 건너뛴다. 이 경로의 프런트 오류 문구와 도움 연결은 검토 항목이다.
4. 대응하는 신호가 없으면 기존 Solar 생성 경로로 진행한다. 규칙이 처리하는 표현은 제한적이라 간접 표현, 오타, 혼합 언어와 문맥에 따라 놓치거나 과하게 막을 수 있다.

Spring은 안내 응답에서 원문 암호문과 재시도 지문을 정리한다. 같은 앱 문맥에 한해 최대 15분 동안 S-16 안내를 조회할 수 있고, 이후 문맥 정보를 정리한다. 이 경로에서 봉인·공개·기록 생성·푸시 발송은 수행하지 않는다.

## 안내 화면 문구 초안과 검증

안내 문구 초안은 “지금 혼자 감당하기 벅찬 마음일 수 있어요. 믿을 수 있는 사람이나 전문 지원에 도움을 요청할 수 있어요”로 제안한다. S-16에는 도움 연결과 홈으로 가기를 둔다. 실제 연결 기관·번호·지역 범위와 최종 문구는 기획과 프런트엔드에서 검토한다. 전화 연결은 사용자가 선택했을 때 실행한다.

검증에는 합성 입력을 사용한다. 명확한 신호, 일반적인 걱정, 인용·타인·과거·부정 맥락, 분기 예외를 확인하고 위기·불확실 결과에서 Solar 호출이 0회인지 검사한다. PostgreSQL 검증에서 걱정 미생성, 임시 입력 정리, 문맥 만료, 삭제 대기·만료 기록의 정리, 늦은 응답 폐기를 확인한다. 실제 사용 환경에서 적용하기 전에는 한국어 간접 표현과 오탐 사례를 추가로 검토하고 S-16 화면 연동을 확인한다.

### 실행 증빙

- Python 테스트 6개 통과. Solar 생성은 테스트 대역을 사용했다. [테스트 코드](../../AI/tests/test_crisis_routing.py)
- Spring 통합 테스트 98개 통과, 실패·오류·건너뜀 각각 0건. 별도 PostgreSQL 17 인스턴스에서 기존 테스트와 신규 정리 테스트 4개를 실행했다. `AnalysisLifecycleTest` 3건과 `VaultCleanupTest` 1건이 통과했다.
- 이 결과는 규칙의 코드 동작과 데이터 처리 경계를 확인한 것이다. 합성 사례에는 기준의 실제 사용자 탐지율이나 임상적 성능을 평가할 데이터가 포함되어 있지 않다.

### Spring과 Python HTTP 연동 검증

별도 PostgreSQL 17 DB에 Spring과 Python을 연결해 기존 게스트 인증과 CSRF 흐름을 거쳐 걱정을 제출했다. Solar 모드의 Python 서비스에서는 외부 모델 생성만 테스트 대역으로 바꿨다. 다음은 2026년 11월 16일 실행 결과다.

- 일반 입력은 `SUCCEEDED`와 걱정 ID를 반환했다. AI 결과 암호문이 저장됐고 생성 호출은 1회였다.
- 직접적인 신호가 있는 합성 입력은 `SUPPORT_GUIDANCE/S16`을 반환했다. 걱정 생성 0건, 임시 입력 암호문 제거, 일반 생성 호출 0회를 확인했다. 다른 게스트·다른 문맥·문맥 없는 조회는 `404`였고, 안내 기한 경과 후에는 원래 문맥에서도 조회가 차단되고 남은 문맥 정보가 정리됐다.
- 모호한 맥락의 합성 입력은 공개 API에서 `FAILED`가 됐다. 걱정 생성과 일반 생성 호출은 각각 0회였다. 임시 입력 암호문이 제거됐다.
- 모델 응답을 보류한 상태에서 금고 전체 삭제를 요청해 `204`를 받았다. 늦은 응답을 풀어 준 뒤 분석 요청과 걱정이 다시 생성되지 않았다.
- Python 모의 모드에서도 일반 성공과 `[mock:guidance]` 응답이 스프링을 거쳐 처리됐다.

프런트 공개 저장소의 검증 시점 `main`에는 걱정 입력 화면이 임시 컴포넌트로 연결되어 있었다. `feat/fe1`과 `feat/fe2`에서도 S-16 라우트와 `SUPPORT_GUIDANCE` 처리를 확인하지 못했다. 실제 브라우저 화면 전환은 해당 구현이 반영된 빌드에서 검증한다.
