# S-16 위기 안내 분기 근거

2026년 11월 16일 기준 구현 초안. 걱정 제출 이후 일반 AI 콘텐츠를 만들기 전에 S-16 안내를 선택할지 결정한다. 임상 판단, 개인의 자살·자해 가능성 예측, 자동 신고와 전화 연결은 이 분기의 범위 밖이다.

## 근거와 구현에 적용한 범위

- WHO는 자살·자해 생각을 심한 고통을 겪는 신호로 설명하고, 삶을 끝내려는 생각이나 계획을 말하는 행동을 주요 신호로 제시한다. 서비스에서는 사용자 본인의 직접적인 표현과 행동·계획 표현을 안내 경로의 후보로 삼는다. [WHO Suicide Q&A](https://www.who.int/news-room/questions-and-answers/item/suicide)
- 미국 NIMH는 죽고 싶다는 말, 자살 계획을 세우거나 방법을 찾는 행동을 경고 신호로 든다. 걱정 제출 텍스트에서 이러한 신호가 직접 드러나면 일반 생성보다 S-16을 앞세운다. 구체적인 수단을 나열하거나 묻는 기능은 없다. [NIMH Warning Signs of Suicide](https://www.nimh.nih.gov/health/publications/warning-signs-of-suicide)
- NICE NG225 1.6절은 위험 점수나 저·중·고 분류를 사용해 미래의 자살·자해를 예측하지 않도록 권고한다. 이 앱은 불안도, 특정 단어 하나, 점수로 S-16 안내를 결정하지 않는다. [NICE NG225 1.6](https://www.nice.org.uk/guidance/ng225/chapter/recommendations#risk-assessment-tools-and-scales)
- 위 근거는 신호와 판단의 한계를 설명한다. 한국어 문구 패턴과 모호한 입력을 어떻게 처리하는지는 [앱의 화면 정책](screen_policy.md#10-위기-대응)을 반영해 정한 구현 규칙이며, 위 기관이 검증한 기준으로 볼 수 없다.

## 앱 분기 조건

1. 걱정 원문을 유니코드 정규화한 뒤 문장 단위로 본다. 불안도와 메모는 판정에 사용하지 않는다.
2. 작성자의 명확한 현재 신호는 `SUPPORT_GUIDANCE`와 `S16`으로 보낸다. 타인 언급이 원인을 설명하는 표현과 타인의 말을 전하는 표현을 구분하고, 이어지는 절에 나온 작성자의 신호를 독립적으로 판단한다. 삶을 이어가고 싶지 않다는 직접 표현은 죽고 싶은 의사를 부정하는 표현과 구분한다.
3. 신호 후보, 모호한 화자·시점·부정·인용 맥락, 규칙 판단 오류는 Solar 분류로 연결한다. R1의 `살기 싫어`, `죽어버리고 싶다`, `손목을 그었어요`와 해당 표현의 일부 띄어쓰기·어미 변형도 후보에 포함한다. `NEEDS_CONTEXT`는 규칙에서 분류 요청을 선택하는 내부 상태다.
4. Solar가 반환할 값은 `GUIDANCE`와 `GENERATE`다. 모델이 본인의 현재 위험 가능성을 배제하기 어려우면 `GUIDANCE`를 선택한다. `GUIDANCE`는 S-16 안내로 연결하고 `GENERATE`는 기존 일반 생성을 실행한다. 이전 형식의 정확한 `{"decision":"NEEDS_CONTEXT"}` 응답만 안내로 복구하고, 그 밖의 잘못된 분류 응답은 `ASSESSMENT_FAILED`로 처리한다. 분류 중 시간 초과·429·일시 장애의 제공자 오류 코드는 보존하여 Spring의 기존 재시도를 적용한다. 분류와 일반 생성은 Python 요청 전체의 제한 시간을 공유하며, 각 요청에는 걱정 원문만 전달한다.
5. 대응하는 신호가 없으면 기존 Solar 생성 경로로 진행한다. 정해진 패턴과 모델의 분류는 간접 표현이나 혼합 문맥에서 누락·오탐이 있을 수 있다.

Spring은 안내 응답에서 원문 암호문과 재시도 지문을 정리한다. 같은 앱 문맥에 한해 최대 15분 동안 S-16 안내를 조회할 수 있고, 이후 문맥 정보를 정리한다. 이 경로에서 봉인·공개·기록 생성·푸시 발송은 수행하지 않는다.

## 안내 화면 문구 초안과 검증

안내 문구 초안은 “지금 혼자 감당하기 벅찬 마음일 수 있어요. 믿을 수 있는 사람이나 전문 지원에 도움을 요청할 수 있어요”로 제안한다. S-16에는 도움 연결과 홈으로 가기를 둔다. 실제 연결 기관·번호·지역 범위와 최종 문구는 기획과 프런트엔드에서 검토한다. 전화 연결은 사용자가 선택했을 때 실행한다.

검증에는 합성 입력을 사용한다. 규칙이 바로 안내를 선택한 경우에는 Solar 호출 0회를 확인한다. 모호한 문맥은 분류 호출을 확인하고, 안내 또는 분류 실패 뒤에는 일반 생성 호출 0회를 확인한다. PostgreSQL 검증에서는 걱정 미생성, 임시 입력 정리, 문맥 만료, 삭제 대기·만료 기록 정리, 늦은 응답 폐기를 확인한다. 실제 사용 환경에서 적용하기 전에는 한국어 간접 표현과 오탐 사례를 추가로 검토하고 S-16 화면 연동을 확인한다.

### 최초 규칙 버전의 Spring과 Python HTTP 연동 검증

별도 PostgreSQL 17 DB에 Spring과 Python을 연결해 기존 게스트 인증과 CSRF 흐름을 거쳐 걱정을 제출했다. Solar 모드의 Python 서비스에서는 외부 모델 생성만 테스트 대역으로 바꿨다. 다음은 2026년 11월 16일 실행 결과다.

- 일반 입력은 `SUCCEEDED`와 걱정 ID를 반환했다. AI 결과 암호문이 저장됐고 생성 호출은 1회였다.
- 직접적인 신호가 있는 합성 입력은 `SUPPORT_GUIDANCE/S16`을 반환했다. 걱정 생성 0건, 임시 입력 암호문 제거, 일반 생성 호출 0회를 확인했다. 다른 게스트·다른 문맥·문맥 없는 조회는 `404`였고, 안내 기한 경과 후에는 원래 문맥에서도 조회가 차단되고 남은 문맥 정보가 정리됐다.
- 모호한 맥락의 합성 입력은 공개 API에서 `FAILED`가 됐다. 걱정 생성과 일반 생성 호출은 각각 0회였다. 임시 입력 암호문이 제거됐다.
- 모델 응답을 보류한 상태에서 금고 전체 삭제를 요청해 `204`를 받았다. 늦은 응답을 풀어 준 뒤 분석 요청과 걱정이 다시 생성되지 않았다.
- Python 모의 모드에서도 일반 성공과 `[mock:guidance]` 응답이 스프링을 거쳐 처리됐다.

### 2026년 11월 18일 #14 생성 지연 재검증

- 사용자 측의 53문장 × 3회 실행에서는 명확한 위험이 48/48회 S-16, 정상 글은 82/84회 일반 분석이었으며, 정상 글 2회가 `PROVIDER_TIMEOUT`이었다.
- 실패에 나온 두 정상 문장과 분류 결과가 달라졌던 모호한 문장을 16회씩 재현했다. 정상 글 32회 중 2회가 시간 초과였다. 두 건에서 분류는 각각 1.257초와 0.642초에 완료됐고, 첫 일반 생성이 남은 요청 시간을 모두 소진했다.
- 첫 보완에서는 일반 생성 첫 시도에 설정된 Python 제한 시간의 절반을 사용했다. 당시 10초 설정에서는 5초이며, 지연되거나 구조화 응답 검증에 실패하면 남은 시간에 한해 한 번 더 요청했다. 제공자의 명시적인 거절과 필터링은 재생성 대상에서 제외한다.
- 문맥 분류에는 `temperature=0`, 일반 생성에는 `temperature=0.2`를 적용하고 각 출력 필드는 짧은 문장으로 작성하도록 한다. 형식 검증과 S-16 분기 계약은 기존 기준을 적용한다. [Upstage Chat Completions API](https://console.upstage.ai/api/chat)
- Python 테스트 21건, 제공자 장애·요청 검증 12건, 격리된 PostgreSQL 17에 연결한 Spring JUnit 98건이 모두 통과했다. 첫 분류·생성 요청이 지연될 때 재시도로 복구되는 경우와 두 요청이 모두 지연돼 전체 제한 시간에 실패하는 경우를 테스트했다.
- 실제 Solar 부하 검증은 합성 문장 53개를 각각 10회 내부 API에 제출했다. 동시 요청 4개에 호출 간격을 설정하지 않은 실행에서는 HTTP 429와 연결된 실패 181회, 별도 생성 시간 초과 4회가 발생했다. 해당 계정의 응답 헤더는 분당 요청 한도 100회를 나타냈다.
