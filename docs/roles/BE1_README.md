# BE1 개발 계획

[통합 개발 계획](../../README.md) · [AI 개발 계획](../../AI/AI_README.md) · [BE2 개발 계획](BE2_README.md)

게스트가 모바일 웹에서 걱정을 맡기고, 서버가 AI 분석을 처리한 뒤 정해진 시각부터 확인할 수 있게 한다. 걱정 접수·봉인, 접근 권한, 공개 상태, 알림, 위기 안내 연동을 담당한다.

## 담당과 스택

**BE1·AI 담당자**가 Java 21, Spring Boot 4.1.x, Spring Security, PostgreSQL로 구현한다. AI는 [Python 계획](../../AI/AI_README.md)에 따라 별도로 구현하고, Spring이 내부 HTTP로 호출하는 구성을 제안한다.

## 첫 구현에서 사용할 설계

- **게스트 인증**은 Spring Security에서 처리한다. 게스트 쿠키를 사용할 경우 운영 HTTPS에서 `HttpOnly`·`Secure`·`SameSite` 설정과 쓰기 API의 CSRF 처리를 프런트엔드와 합의한다. 서비스와 조회 쿼리에서 요청·기록의 소유권을 검사한다. [Spring Security의 CSRF 보호](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)
- **분석 접수**는 PostgreSQL에 요청과 처리 상태를 커밋한 뒤 요청 ID를 반환한다. 게스트 범위의 제출 키에 유일 제약을 두고, 동일 키의 재전송과 별도 제출을 구분한다. 동일 키에 다른 내용이 들어온 경우의 오류도 API에서 정의한다.
- **비동기 실행**은 PostgreSQL 작업 테이블에서 처리할 건을 짧은 트랜잭션으로 선점하는 방식을 먼저 검토한다. Python 호출은 트랜잭션 밖에서 실행하고, 작업 만료 후 복구할 수 있도록 선점 기한과 시도 식별자를 둔다. 처리 중인 요청을 계속 보관할 조건과 재시도 한도는 ERD·API와 함께 정한다.
- **결과 저장** 직전에 현재 처리 시도, 삭제·만료, 게스트 상태를 트랜잭션 안에서 검사한다. 걱정·콘텐츠 저장과 요청 성공 전환은 함께 커밋한다. BE2의 삭제 흐름과 같은 잠금 순서나 조건부 갱신 규칙을 합의해 지연 응답이 삭제 상태를 덮어쓰는 경우를 막는다.
- **시간 판정**에는 서버 시계를 사용한다. 공개·만료 시각은 PostgreSQL의 `timestamptz`로 저장하는 방향을 제안하고, 기본 오전 8시 계산에 사용할 사용자 시간대 식별자는 API에서 따로 정한다.

## 구현 순서

| 순서 | 범위 | 구현할 내용 | 완료 기준 |
| --- | --- | --- | --- |
| 0 | ERD·API·로컬 실행 | 게스트·분석 요청·걱정·AI 콘텐츠의 ERD와 공개 API 초안을 작성한다. BE2와 공통 마이그레이션 방식, Python 가짜 응답 계약을 공유한다. | 로컬 PostgreSQL에 초기 스키마를 적용할 수 있고, 프런트엔드와 BE2가 요청·응답 예시로 개발을 시작할 수 있다. |
| 1 | 게스트 인증·접근 제어 | 브라우저 기반 게스트 생성과 유효 세션 재사용, 인증 오류와 새로 시작하기, 유효 접속 시 기본 30일 갱신을 구현한다. BE2도 사용하는 공통 인증·소유권 검사를 만든다. | 같은 브라우저에서 금고·설정이 복원된다. 다른 게스트의 기록·요청 ID로 조회·변경할 수 없고 URL에 인증 정보가 노출되지 않는다. |
| 2 | 입력·공개 시각 | 걱정은 공백 제외 최소 1자·공백 포함 최대 500자, 불안도는 1~5, 메모는 선택·최대 100자로 검증한다. 기본 공개 시각은 현지 오전 8시로 시작한다. 제출과 시각 변경 시 미래이며 만료 전에 공개되는지 서버가 검증한다. | 입력 화면의 다음 버튼만으로 서버 기록이 생기지 않는다. 제출과 변경에 같은 서버 기준을 적용하고, 공개된 기록은 다시 잠기지 않는다. |
| 3 | 접수·비동기 분석 | 접수 ID를 반환하고 AI 호출을 서버 작업으로 실행한다. 접수 여부가 불명확한 재전송과 별개 걱정의 새 제출을 구분한다. 상태 조회와 최종 실패 후 사용자 재시도를 지원한다. | 화면을 나가도 접수된 작업이 계속된다. 응답 유실·중복 요청에도 걱정 하나만 생성되고, 성공한 요청을 다시 열어도 AI를 다시 호출하지 않는다. |
| 4 | 봉인·홈·공개 | AI 결과를 검증해 저장하고, 저장 성공 뒤 봉인 상태를 반환한다. 홈의 요청 상태와 금고 개수를 분리하고, 공개 목록과 잠긴 목록을 각각 최신순으로 제공한다. | 잠긴 항목에는 허용된 메타데이터만 반환한다. 저장 시 이미 공개 시각을 지났다면 바로 공개 가능 상태가 된다. 목록 조회와 실제 상세 열람이 구분된다. |
| 5 | 위기 안내·실패 정리 | AI의 위기 안내 결과를 S-16에 연결하고 일반 저장·알림을 차단한다. 앱 안에서 결과를 받을 때만 안내 진입을 제공한다. 최종 실패 후 서버 임시 원문을 지우고 내용 없는 실패 상태는 접수 후 최대 24시간 보인다. | 위기 결과가 일반 기록에 남지 않고 브라우저 종료 후 푸시·입력 복원이 없다. 초안이 없으면 재입력을 요청하고 재시도 시 공개 시각을 재검증한다. |
| 6 | 공개 알림·재알림·설정 | 공개 알림은 첫 등록 때 한 번 제안하며 기본은 꺼짐이다. 동의·브라우저 권한·구독을 구분한다. 같은 공개 시각의 기록은 묶고, 재알림은 사용자가 요청한 30분·1시간 중 활성 예약 하나만 둔다. | 알림 없이도 봉인된다. 재알림 교체 실패 시 기존 예약이 유지되고, 두 알림이 같은 시각이면 공개 알림만 발송한다. 알림 문구에 민감 정보가 없다. |
| 7 | 삭제·만료 연동과 통합 점검 | BE2의 삭제·만료 흐름에 예약 취소, 작업 중단, 늦은 AI 결과 폐기, 전체 삭제 후 인증 제거를 연결한다. 원문·모델 응답·인증 정보 없이 접수·저장 시간과 상태를 측정한다. | 삭제 중·만료된 기록이 다시 조회되거나 늦은 결과로 재생성되지 않는다. 부분 실패 후 재처리할 수 있고 전체 삭제 성공 뒤에 인증을 제거한다. |

## 제출과 공개에서 합의할 규칙

- 접수 확인 전 통신 오류에는 같은 제출을 식별할 값을 사용한다. 사용자 재시도는 서버가 최종 실패를 확정한 뒤에만 제공하고, 최초 접수 시각 기준 30일 보관 기한은 유지한다.
- 15초는 지연 안내 기준이다. 30초가 지나면 상태를 확인한 뒤 홈에 반영한다. 작업 자체의 제한 시간, 서버 자동 재시도, 중단된 작업의 복구 방식은 별도로 정한다.
- 공개 일시는 서버 시각으로 판정하고 사용자 현지 시간대로 표시한다. 공개 전 시간 변경은 알림 예약도 갱신한다. 변경 도중 공개되면 공개 상태를 반환한다.
- 최초 상세 열람은 금고 상세와 기록 상세에서 공통으로 기록한다. 목록에서 요약만 본 경우에는 미확인 상태를 유지한다.
- 공개 알림은 발송 직전에 동의·구독·열람·삭제·만료·중복 여부를 검사한다. 공개 시각 이후에 분석이 저장된 건은 제출 당시 동의와 현재 유효한 구독 등 조건을 충족할 때 공개 가능 알림을 한 번 예약한다. 전송 요청 결과와 실제 도착·열람을 구분한다.
- 개별·전체 삭제 처리와 분석 성공 저장이 동시에 실행되는 경우에도 삭제된 기록의 신규 저장을 막을 수 있게 BE2와 상태 검사 방식을 합의한다.
